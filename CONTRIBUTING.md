# Работа над Zero: правила для людей и их агентов

Zero — мобильное приложение (PWA) для общих трат с друзьями: кто платил, как делим, кто кому сколько должен. Вход только через Telegram. Рабочий проект используют реальные люди, поэтому правила про заливку и базу ниже важны.

Что уже сделано, что в планах и какие решения приняты — в [docs/PROJECT-NOTES.md](docs/PROJECT-NOTES.md). Прочитай его перед тем, как предлагать новую функцию.

## Запуск у себя

```bash
git clone https://github.com/dlvolgin42/zero.git
cd zero
npm install
npm run dev        # http://localhost:3000
```

Без базы данных приложение открывается в демо-режиме: кнопка «Войти в демо» даёт тестовых друзей и траты. Настоящий вход через Telegram и сохранение данных локально не работают (нужны Postgres и ключи). Для большинства правок интерфейса демо достаточно. Проверяй размер телефона (375 px по ширине): приложение делается под iPhone и Android.

Перед отправкой кода: `npm run build` должен проходить без ошибок.

## Стек

Next.js 16 (App Router, Turbopack, Cache Components, `output: "standalone"`), React 19, TypeScript, Tailwind v4, Konsta UI, Postgres 17, драйвер `postgres`, `jose` для проверки токенов Telegram. Развёртывание: Docker Compose на VPS.

Важные особенности:
- **Деньги** хранятся целыми числами в минимальных единицах (копейки, центы) плюс трёхбуквенный код валюты. Дробных сумм в коде нет.
- **Route handlers (`app/api/**`)**: сначала читай cookies, заголовки и `searchParams`, и только потом открывай `try/catch`. Иначе Next проглотит свой служебный сигнал и маршрут сломается. Для общих проверок есть обёртка `withMe` в `lib/server/http.ts`.
- Типы для `[id]`-маршрутов создаются командой `npx next typegen`.
- Клиент называет вошедшего человека `"me"`, а сервер подставляет настоящий id. Не смешивай их.
- Изменения на клиенте идут оптимистично: сначала экран, потом запрос на сервер, потом `refresh()`.
- Схема базы живёт в `db/migrations/`. Меняешь схему — добавляй **новый** файл `000N_*.sql`, старые не правь. Сумма платежей и сумма долей в трате сверяются триггером в базе.
- Весь код, комментарии, имена файлов и коммиты — на английском. Тексты в интерфейсе — на русском.

## Как вести работу в git

- Работаем прямо в `main`: коммитим и пушим в него, без отдельных веток и pull request'ов.
- Отдельную ветку (`feature/...` или `fix/...`) и pull request делай, только если человек явно об этом попросил.
- Перед началом работы и перед пушем подтягивай свежий `main` (`git pull`): в него пушат двое. При конфликте сливай (merge), а не переписывай историю.
- Коммиты маленькие, с понятным сообщением на английском. Не переписывай историю в `main` и не делай `push --force`.
- Не трогай чужую работу рядом: заметил проблему не по теме — напиши отдельным пунктом или заведи issue, не правь «по дороге».

## Секреты

- Никогда не коммить `.env`, ключи, токены, пароли, адреса серверов. `.gitignore` уже закрывает `.env*` и `deploy/local.env`.
- Client Secret Telegram и пароль базы лежат только на сервере. Не вставляй их в чат, issue или pull request, и не печатай значения в логах. Если нужно проверить, что переменная задана, проверяй только наличие и длину.
- Адрес сервера и публичный адрес приложения хранятся в `deploy/local.env` (в git его нет). Образец — `deploy/local.env.example`. Значения передавай друг другу лично.

## Заливка на сервер

Сервер один, и база на нём настоящая: там данные живых людей.

1. Перед заливкой убедись, что `npm run build` проходит, и проверь изменение локально (в размере телефона).
2. Заливать можно сразу, разрешение спрашивать не нужно, это относится к вам обоим. Но не заливай после каждой мелочи: собирай правки в разумные пачки, каждая заливка занимает время и перезапускает приложение. Если вы оба правите одновременно, коротко предупредите друг друга, чтобы заливки не наложились.
3. Заливка: `./deploy/deploy.sh` из папки проекта. Скрипт собирает локально, `rsync` отправляет только изменившееся, на сервере поднимает контейнеры. Нужен файл `deploy/local.env` и ssh-доступ к серверу.
4. После заливки проверь: контейнеры здоровы (`docker compose ps` на сервере), в логах нет ошибок, сайт открывается по публичному адресу.
5. Миграции базы применяются автоматически при заливке. Не делай разрушающих операций с базой (`drop`, `truncate`, массовые `delete`) без явной договорённости и свежей копии: ежедневные дампы лежат на сервере в `~/app/backups`.

## Поведение агентов (предложение, можно поправить под себя)

- Делай то, о чём просили. Не меняй, не удаляй и не создавай ничего сверху. Заметил проблему рядом — скажи и спроси.
- Если правка вышла за рамки просьбы, сразу скажи об этом и спроси, оставлять или откатывать. Откатывать самому не нужно.
- Факты о внешних системах (Telegram, Facebook, библиотеки) проверяй по источнику, а не по памяти. Нельзя проверить — так и скажи.
- Результат показывай, а не описывай: скриншот, вывод команды, замер.
- Ошибку признавай одной фразой и исправляй.
- Отчёт короткий: что сделано, что отклонилось от просьбы, что осталось. После заливки одной строкой скажи, что залито.
- Если развилка меняет результат — спроси, рекомендуемый вариант назови первым. Если не меняет — реши сам и отметь как своё решение.
